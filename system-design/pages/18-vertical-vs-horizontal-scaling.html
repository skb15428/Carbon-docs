Vertical vs horizontal scaling

When one server can't keep up, you either buy a bigger machine (scale up) or add more machines that share the work (scale out). This page covers both, plus everything that breaks when you scale out: sessions, the database and sudden spikes.

7 subtopicsstepsquestions

Scale up: one bigger machine

Simple, no code changes, but has a ceiling and a single point of failure.

Scale out: more machines

No ceiling and survives failures, but servers must be stateless.

If you remember nothing else

  1. Scale up first for speed; design to scale out because of the ceiling and the single point of failure.
  2. Plan peak at 60–70% busy per server, plus one spare (N+1).
  3. Make servers stateless before scaling out: sessions go to Redis or into JWTs.
  4. More app servers move the bottleneck to the database: pooler, cache, then read replicas.
  5. Autoscaling lags by minutes: pre-scale known spikes; scale out fast and in slowly.

How to answer any scaling question

1. CauseWhat is actually overloaded, and why.
2. FixWhat you would change, in order.
3. Trade-offWhat the fix costs or breaks.
4. NumberA quick estimate: servers, connections, minutes.

Common trap: explaining the cause well and then stopping. Always finish with the fix and the reason it works. Interviewers care more about the fix than the cause.

Subtopic 1 of 7

Overload, queueing and headroom

Why a server gets slow long before it's “full”, what users see when it is full, and how much spare capacity to keep.

Remember

  • Utilisation = requests per second ÷ capacity (200 ÷ 1,000 = 20%).
  • Waiting grows like busy ÷ (1 − busy): ×1.5 at 60%, ×9 at 90%, ×19 at 95%. Latency shoots up near the limit.
  • Above 100% the queue grows forever: 504 when requests time out, 503 when the server refuses them. Retries make it worse.
  • Plan normal peak at 60–70% busy, keeping 30–40% headroom for bursts, retries, deploys and failures.
  • When overloaded, fail fast with 503s (load shedding) instead of letting everyone time out.
Python: how waiting grows with load
# How long a request waits, as a multiple of the work time (M/M/1 queue)
def wait_factor(busy):
    if busy >= 1:
        return float("inf")   # arrivals beat capacity: the queue grows forever
    return busy / (1 - busy)

for busy in (0.2, 0.6, 0.7, 0.85, 0.9, 0.95):
    print(f"{busy:.0%} busy -> wait x{wait_factor(busy):.1f}")
# 20% x0.2 | 60% x1.5 | 70% x2.3 | 85% x5.7 | 90% x9.0 | 95% x19.0

Subtopic 2 of 7

Vertical scaling: a bigger machine

The quickest fix, and the three walls you hit with it: the ceiling, the single point of failure, and downtime.

Remember

  • Vertical scaling (scaling up) = the same app on a bigger machine: more cores, memory, faster disks.
  • Advantages: no code changes, nothing new to run, fastest first fix. Great for databases.
  • Limits: a hard ceiling (the biggest machine), rising cost, a single point of failure, and downtime on every resize.
  • A 2× bigger machine is often less than 2× faster (locks, single-threaded code, memory bandwidth).
  • Interview line: “Scale up first for speed, but design to scale out.”

Subtopic 3 of 7

Horizontal scaling: more machines

A load balancer spreads requests across identical servers. Health checks route around failures, N+1 keeps a spare, and the load balancer itself needs a backup.

Remember

  • Horizontal scaling (scaling out) = more identical servers behind a load balancer.
  • Advantages: no ceiling, small cheap steps, survives a server dying.
  • Load balancer picks a server by round robin, least connections or hashing; health checks remove dead servers within seconds.
  • N+1: servers = ceil(peak ÷ (capacity × 0.7)) + 1. 14,000/s at 1,000 each → 20 + 1 = 21.
  • The load balancer must be redundant: an active–passive pair sharing a floating IP with heartbeats, or a managed one (AWS ELB).
  • Costs: servers must be stateless, the shared database becomes the bottleneck, more to deploy and monitor.
Python: servers needed and a round-robin load balancer
import math, itertools

def servers_needed(peak_rps, per_server=1000, target=0.70, spare=1):
    """Servers to run so peak sits at `target` busy, plus spares (N+1)."""
    safe = per_server * target                # 1,000 * 0.7 = 700 requests/s
    return math.ceil(peak_rps / safe) + spare

print(servers_needed(14_000))   # 20 + 1 = 21
print(servers_needed(6_000))    # 9 + 1 = 10
print(servers_needed(2_400))    # 4 + 1 = 5

class LoadBalancer:
    """Round robin that skips servers failing their health check."""
    def __init__(self, servers):
        self.servers = list(servers)
        self.healthy = set(self.servers)
        self._next = itertools.cycle(self.servers)

    def health_check(self, server, ok):
        if ok:
            self.healthy.add(server)
        else:
            self.healthy.discard(server)

    def pick(self):
        for _ in range(len(self.servers)):
            server = next(self._next)
            if server in self.healthy:
                return server
        raise RuntimeError("503: no healthy servers")

lb = LoadBalancer(["s1", "s2", "s3"])
lb.health_check("s2", ok=False)
print([lb.pick() for _ in range(4)])   # ['s1', 's3', 's1', 's3']

Subtopic 4 of 7

Stateless servers and sessions

Why users get logged out at random after you add servers, why sticky sessions are a trap, and the two real fixes.

Remember

  • Sessions in each server's memory + a load balancer = random logouts: the next request lands on a server that doesn't know the user.
  • Sticky sessions are a patch: a crash or deploy logs out everyone on that server, and load becomes uneven.
  • Fix 1: a shared session store (Redis, with a replica and TTLs). Fix 2: signed tokens (JWT), short expiry plus refresh token.
  • Stateless servers keep nothing between requests, so any server can serve any request. This is what makes autoscaling and rolling deploys safe.
  • Files go to object storage (S3), not the server's disk.
Python: sessions in Redis
import json, secrets
import redis   # pip install redis

store = redis.Redis(host="sessions.internal", port=6379)

def login(user_id):
    session_id = secrets.token_urlsafe(32)
    store.set(f"session:{session_id}", json.dumps({"user_id": user_id}), ex=3600)
    return session_id          # sent to the browser in a cookie

def current_user(session_id):
    data = store.get(f"session:{session_id}")   # any server can do this
    return json.loads(data)["user_id"] if data else None   # None -> login page

def logout(session_id):
    store.delete(f"session:{session_id}")       # instant logout everywhere

Subtopic 5 of 7

App servers vs the database

Once app servers scale easily, the one shared database takes the strain. Here's why more servers can make things slower, and the fixes in order.

Remember

  • Stateless app servers scale easily; the shared database becomes the bottleneck.
  • Database connections = app servers × pool size: 20 × 50 = 1,000. Too many connections and concurrent queries make everything slower.
  • Fix order: slow queries and indexes → PgBouncer → cache hot reads (80% hits = 5× fewer reads) → read replicas → scale up the primary → shard.
  • Replication lag: a read right after a write can hit a replica that hasn't caught up (the old profile photo).
  • Fix with read-your-own-writes: send a user's reads to the primary for a few seconds after they write.
  • Replicas scale reads, not writes.
Python: cache-aside and read-your-own-writes routing
import json, time

# 1. Cache-aside: check the cache, fall back to the database, then fill the cache
def get_profile(user_id):
    key = f"profile:{user_id}"
    cached = cache.get(key)
    if cached:
        return json.loads(cached)                                  # hit: about 1 ms
    row = replica.query("SELECT * FROM users WHERE id = %s", user_id)  # miss
    cache.set(key, json.dumps(row), ex=300)                        # keep for 5 minutes
    return row

# 2. Read your own writes: recent writers read from the primary
STICKY_SECONDS = 5          # longer than normal replication lag
last_write = {}             # user_id -> time of last write (keep in Redis in production)

def pick_db(user_id, is_write):
    if is_write:
        last_write[user_id] = time.time()
        return "primary"
    if time.time() - last_write.get(user_id, 0) < STICKY_SECONDS:
        return "primary"    # sees their own new photo
    return "replica"

print(pick_db(42, is_write=True))    # primary (uploads a new photo)
print(pick_db(42, is_write=False))   # primary (sees the new photo)
print(pick_db(7, is_write=False))    # replica (everyone else)

Subtopic 6 of 7

Autoscaling and sudden spikes

The cricket final story: why autoscaling still lets users see errors, how pre-scaling fixes it, and why you scale in slowly.

Remember

  • Target tracking: keep average CPU near 60–70%; set a minimum (availability) and a maximum (cost).
  • Servers needed = ceil(traffic ÷ (capacity × target)): 15,000 ÷ 650 → 24.
  • Autoscaling reacts after the spike, and a new server needs 2–5 minutes to boot and warm up (cold start).
  • Known spikes: pre-scale on a schedule 15–20 minutes early. Keep a warm pool for surprises.
  • While capacity catches up: waiting room, rate limiting, graceful degradation.
  • Scale out fast, scale in slowly: a cooldown stops flapping, and draining lets in-flight requests finish.
Python: a target-tracking autoscaler with a cooldown
import math, time

def desired_servers(rps, per_server=1000, target=0.65, min_n=2, max_n=100):
    need = math.ceil(rps / (per_server * target))
    return max(min_n, min(max_n, need))

print(desired_servers(3_000))    # 5
print(desired_servers(15_000))   # 24

def autoscaler(get_rps, running, start, drain_and_stop, cooldown_s=300):
    last_scale_in = 0
    while True:
        want, have = desired_servers(get_rps()), running()
        if want > have:
            start(want - have)                   # scale out: fast, all at once
        elif want < have and time.time() - last_scale_in > cooldown_s:
            drain_and_stop(1)                    # scale in: one at a time
            last_scale_in = time.time()
        time.sleep(60)

The interview ladder: scaling step by step

When they ask “how would you scale this?”, climb these nine steps in order. At each one say what's overloaded, what you change, and what it costs.

Remember the ladder

  • 1 One server → 2 Measure the bottleneck → 3 Scale up → 4 Split app and database → 5 Stateless servers
  • 6 Load balancer + N+1 servers → 7 Database becomes the bottleneck → 8 Cache + read replicas → 9 Autoscale + pre-scale
  • After that: sharding, CDN, multiple regions (later lessons).
